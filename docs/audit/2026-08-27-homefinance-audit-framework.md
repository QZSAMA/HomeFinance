# HomeFinance 深度审查分析框架

## 研究概览

- **研究对象**：HomeFinance 家庭财务管理系统
- **审查基线**：`main@b103e4221ae58d2cd09ee586d69f3cf90c79c146`
- **范围**：前端、后端、数据模型、基础设施、测试、CI/CD、文档、功能完整性与产品推进机会
- **分析域**：软件架构审查、代码质量审查、产品功能审查、工程治理与路线规划
- **核心问题**：
  1. 当前系统的真实架构、关键数据流、模块边界和运行约束是什么？
  2. 已声明功能与代码、测试、部署配置之间是否一致，哪些风险会影响正确性、安全性、可维护性和用户体验？
  3. 如何建立可持续更新的项目记忆，并以测试驱动方式推进整改和新功能？

## 框架选择

| 分析章节 | 采用框架 | 应用方式 |
|---|---|---|
| 架构与模块边界 | 价值链分析 + 依赖图谱 | 从用户操作到 API、数据库、缓存和对象存储追踪端到端价值流，并识别跨层耦合 |
| 质量与风险 | ISO/IEC 25010 质量属性映射 + OWASP 风险视角 | 从功能适合性、可靠性、性能、安全性、可维护性、可移植性等维度评估实证 |
| 功能完整性 | JTBD + 声明—实现—测试三角校验 | 将家庭财务任务映射到页面、API、数据实体和自动化测试，识别断点与名实偏差 |
| 推进策略 | SWOT + 影响/投入矩阵 | 汇总优势、债务、机会与威胁，并形成分阶段、可验收、可度量的路线图 |

## 1. 架构、数据与运行模型

- **分析目标**：还原系统边界、组件职责、依赖方向、核心实体及关键业务数据流。
- **分析逻辑**：入口与部署 → 前后端模块 → 中间件与服务 → 数据/缓存/文件存储 → 外部 AI 服务。
- **核心假设**：系统采用模块化单体，但路由层承担了较多业务职责，边界和事务一致性可能成为扩展瓶颈。

### 数据要求

| # | 指标/证据 | 类型 | 来源 | 优先级 |
|---|---|---|---|---|
| 1 | 目录、文件、代码行、模块依赖与高连接节点 | 定量+定性 | Git、源码、Graphify AST | P0 |
| 2 | Express 路由、中间件顺序、服务调用与外部依赖 | 定性 | `backend/src` | P0 |
| 3 | React 路由、页面、状态管理、API 服务映射 | 定性 | `frontend/src` | P0 |
| 4 | Prisma 实体、关系、索引、级联与迁移一致性 | 定性 | Prisma schema/migrations | P0 |
| 5 | Docker、环境变量、CI/CD 与运行拓扑 | 定性 | compose、Dockerfile、workflows | P1 |

- **图 1**：系统上下文与容器图——浏览器、前端、后端、PostgreSQL、Redis、MinIO、AI Provider。

- **论证结构**：现状（What）→ 形成原因（Why）→ 对演进的含义（So What）。

## 2. 工程质量、安全与性能

- **分析目标**：验证代码、依赖、构建、测试和生产配置是否达到可维护、可运行和可防护的最低基线。
- **分析逻辑**：可复现构建 → 自动化测试 → 静态扫描 → 关键路径代码审查 → 运行时验证。
- **核心假设**：后端测试数量较多，但前端测试、端到端测试、覆盖率门禁与生产安全默认值不足。

### 数据要求

| # | 指标/证据 | 类型 | 来源 | 优先级 |
|---|---|---|---|---|
| 1 | 后端测试套件、用例数、失败项、覆盖率 | 定量 | Jest | P0 |
| 2 | 前后端构建、lint、TypeScript 诊断 | 定量+定性 | npm scripts | P0 |
| 3 | 依赖漏洞、许可证/版本风险 | 定量+定性 | npm audit、lockfiles | P0 |
| 4 | 鉴权、授权、输入校验、文件上传、AI action、秘密管理 | 定性 | 源码与配置 | P0 |
| 5 | 查询形态、缓存 TTL/失效、并发、事务、分页与 N+1 | 定性 | 源码与 Prisma | P1 |
| 6 | React 请求瀑布、重渲染、bundle、可访问性 | 定性 | 前端源码、构建产物、浏览器 | P1 |

### 可视化与内容计划

- **图 3**：质量雷达——功能、可靠性、性能、安全性、可维护性、可运维性（仅使用审查证据评分）。
- **对照表**：发现、严重度、证据位置、影响、修复建议、建议测试。
- **论证结构**：可观察事实 → 失效场景/攻击路径 → 用户与业务影响 → 整改控制。

## 3. 功能覆盖与用户任务

- **分析目标**：核实 README 声明的功能是否在 UI、API、数据模型和测试四层闭环。
- **分析逻辑**：JTBD → 页面 → API → 数据实体 → 测试 → 运行时结果。
- **核心假设**：核心财务账本和报表已形成闭环，但部分“智能”“离线”“权限”能力可能只达到局部实现。

## 4. 持续记忆、治理与推进路线

- **分析目标**：建立可在后续会话和代码变更后持续更新的项目知识与决策机制。
- **分析逻辑**：结构化事实层 → 图谱关系层 → 决策/风险层 → 增量更新触发器 → 验收门禁。
- **核心假设**：单一 Wiki 会快速过期，需要 Graphify 图谱、轻量项目记忆、ADR、审查台账和 CI 指标共同维护。

### 数据要求

| 3 | CI 现状与可加入的质量门禁 | 定性 | GitHub Actions | P1 |
| 4 | 整改项的影响、投入、依赖、验收指标 | 混合 | 审查发现 | P0 |

## 数据采集任务清单

1. 锁定 Git 基线、目录结构、代码规模、提交节奏和文档声明。
2. 解析前后端入口、路由、服务、状态、Prisma 模型、部署和 CI。
3. 生成 Graphify HTML/JSON/审计报告并配置增量更新规则。
4. 使用干净安装运行测试、构建、lint、依赖审计和覆盖率采样。
5. 对认证授权、财务计算、缓存、文件、导入导出、AI/OCR 与前端关键路径进行深读。
6. 在依赖服务可用时执行本地 API/UI 冒烟测试；不可用时明确记录缺口。
7. 汇总发现并以 P0/P1/P2/P3 分级，给出 TDD 化修复验收用例。
8. 输出架构/功能审查报告、项目记忆规则和分阶段推进方案。

## 质量门槛

- 所有重大结论必须至少指向一个源码位置、测试输出或配置证据。
- 不把“测试存在”等同于“功能正确”，不把“构建通过”等同于“可生产部署”。
- 缺少运行环境或数据时明确标注“未验证”，不推测通过。
- 后续代码变更必须遵循 RED → GREEN → REFACTOR；每个整改项先建立能复现风险的失败测试。
