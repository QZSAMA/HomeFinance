# P1-G-04 Playwright E2E Closure Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task with review checkpoints.

**Goal:** Obtain a real green GitHub Actions run for all four P1-G-04 Playwright journeys and record the evidence without changing production financial behavior.

**Architecture:** Keep `.github/workflows/e2e.yml` as a thin CI entry point and keep Compose lifecycle in `frontend/scripts/run-e2e.mjs`. Diagnose failures from service health, browser artifacts, and HTTP responses in that order; make the smallest change in the E2E spec, runner, Compose health checks, or workflow, then rerun the complete suite.

**Tech Stack:** Playwright 1.62, Chromium, Node.js 20, Docker Compose, PostgreSQL 16, Redis 7, MinIO, deterministic mock-AI, GitHub Actions, React/Vite frontend, Express/Prisma backend.

## Global Constraints

- No changes to financial semantics, authorization policy, persistence schema, or production API behavior.
- No production secrets or external AI provider calls; the E2E stack uses disposable volumes and `e2e/mock-ai`.
- No hidden test skip, arbitrary sleep, or weakened assertion; HTTP status and resulting UI state remain asserted.
- P1-G-04 is `PASS-E2E` only after a real GitHub runner executes all four journeys green in one run.
- P1-G-05 Redis/MinIO failure recovery, object isolation, staging, release observation, and Graphify semantic refresh remain outside this plan.
- Preserve the existing 60% backend coverage threshold and the current frontend warning/bundle gates.

- [ ] **Step 1: Classify the failure from evidence**

Use the first matching category and record it in the commit message/evidence:

```text

navigation       -> frontend reachability or API proxy
selector-state   -> UI locator, family selection, or async state synchronization
contract         -> unexpected HTTP status, response path, or returned data
cleanup          -> teardown/artifact handling only
```

Expected: exactly one primary category and one concrete failing assertion/request.

- [ ] **Step 2: Write a focused failing check before changing the implicated file**

For a selector/state or contract failure, run the existing journey in isolation and preserve the failure:

```powershell

```

For a service-health failure, reproduce the config/health command directly:


Expected: the same failure is observed locally or the missing local Docker capability is recorded without claiming a code defect.

- [ ] **Step 3: Apply the smallest test-topology fix**

Use these exact rules:

```text

contract: match the complete URL pathname and expected status; do not accept any 2xx response from a neighboring endpoint.
service-health: probe 127.0.0.1 inside the container or a service name on the Compose network; keep the existing retry budget.
runner/cleanup: preserve E2E_KEEP_STACK diagnostics and keep teardown under if: always().
```

Do not alter backend route semantics, relax authorization assertions, or convert a missing ledger row into a soft pass.
